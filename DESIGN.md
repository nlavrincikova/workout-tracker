## Part 1 — Workout Tracker

### 1.1 Goal & Scope

A chat-driven AI Agent that logs workouts into a structured database, keeps a clean catalog of exercises, classifies workouts by type, and supports future analytics and recommendations.

Phase 1 uses Google Sheets as the backend for ease of debugging. Phase 2 will migrate to Notion with minimal workflow changes.

### 1.2 Data Model

**A. `exercise_list` — Master catalog (dimension table)**

| Column | Description | Notes |
|---|---|---|
| exercise_id | Unique integer ID | Primary key, auto-incremented by n8n |
| exercise_name | Canonical exercise name | Must be unique (case-insensitive) |
| exercise_body_part_focus | Main body area targeted | core / full body / lower body / upper body |
| exercise_primary_equipment | Equipment required | Nullable |
| exercise_movement_pattern | Movement classification | Squat / Hinge / Pull / Push / Carry / Rotate |
| exercise_intensity_type | Intensity category | Reps / Time / Load / AMRAP |
| exercise_description | One-sentence description | AI-generated by ai_agent_exercise_info |
| exercise_muscles_worked | Muscles targeted | AI-generated |
| exercise_key_cues_safety | Safety and form cues | AI-generated, optional |
| exercise_non_machine_alternative | Bodyweight alternative | AI-generated, optional |
| exercise_name_normalized | Lowercase singular name | Used for fuzzy matching in generator |
| exercise_frequency | Total times logged | Incremented by n8n after each confirmed workout |

**B. `workout_type` — Classification reference table**

| Column | Description | Notes |
|---|---|---|
| workout_type_id | Unique integer ID | Primary key |
| workout_type_name | Workout classification | e.g. full body, lower body, core. Unique, case-insensitive |

**C. `workout_exercise` — Fact table (transaction log)**

| Column | Description | Notes |
|---|---|---|
| workout_id | Session ID | Groups all exercises from one session |
| workout_date | Date of workout | Format: YYYY-MM-DD |
| workout_type_id | FK to workout_type | Required |
| exercise_id | FK to exercise_list | Required |
| workout_rounds | Number of rounds performed | Required |
| workout_repetition_type | Type of repetition | reps / time / amrap |
| workout_repetition_amount | Amount performed | Integer for reps, string for time (e.g. 30 sec) |
| workout_type_name | Calculated column | ARRAYFORMULA VLOOKUP from workout_type tab |
| workout_exercise_name | Calculated column | ARRAYFORMULA VLOOKUP from exercise_list tab |

### 1.3 Key Design Principles

**Separation of Responsibilities**
- **AI Agent decides:** exercise parsing and normalization, metadata generation for new exercises, workout type inference.
- **n8n enforces:** deduplication rules, ID generation, referential integrity, write order (dimension tables before fact tables).

**ID Strategy**
- All IDs are integers, auto-incremented by n8n using `max(existing) + 1`.
- New exercises are temporarily written with `PENDING` as the exercise_id placeholder.
- A subsequent Google Sheets Update node replaces `PENDING` with the calculated real ID.
- IDs are never generated by the AI agent.

**Deduplication Rules**

| Entity | Rule |
|---|---|
| Exercise | Case-insensitive exercise_name match. Falls back to exercise_name_normalized for plural/singular variants |
| Workout type | Case-insensitive workout_type_name match |
| Workout session | New workout_id generated per prompt execution — no deduplication |

### 1.4 n8n Workflow — LOG Flow

**Flow Summary**
1. Chat trigger → `ai_agent_prompt_process` parses workout into JSON
2. `route_by_intent` routes log intent to FALSE branch → `if_log_or_confirm` routes to `code_json_output`
3. `code_json_output` expands exercises array into individual items
4. `split_out_exercise` + `edit_exercise_name` normalizes each exercise name
5. `get_exercise_list` + `code_exercise_match` checks each exercise against catalog
6. New exercises: `ai_agent_exercise_info` generates metadata → `append_new_exercise` writes PENDING row → `code_exercise_id` calculates real ID → `update_exercise_id` replaces PENDING
7. All exercises merge → `get_workout_exercise` + `get_workout_types` → `code_workout_exercise` builds fact table rows
8. `append_workout_exercise` writes to workout_exercise → frequency counter increments → success message sent

### 1.6 Google Sheets ARRAYFORMULA Columns

The `workout_exercise` tab has two calculated columns. Formulas live in row 2 (not the header row, due to Google Sheets Table constraints) and auto-populate for all rows appended by n8n.

- **workout_type_name:** `=ARRAYFORMULA(IF(ISBLANK(C2:C), "", IFERROR(VLOOKUP(C2:C, workout_type!$A$2:$B$30, 2, FALSE), "Not Found")))`
- **workout_exercise_name:** `=ARRAYFORMULA(IF(ISBLANK(D2:D), "", IFERROR(VLOOKUP(D2:D, exercise_list!$A$2:$B$1000, 2, FALSE), "Not Found")))`

## Part 2 — Workout Generator

### 2.1 Goal & Scope

A read-analyze-suggest pipeline that generates tailored workout suggestions based on historical performance and catalog availability. No data is written to workout_exercise until the user explicitly confirms the suggestion.

### 2.2 Additional Data Model

**D. `staged_workout` — Session staging table**

| Column | Description | Notes |
|---|---|---|
| session_id | Chat session identifier | From When chat message received node sessionId field |
| exercises_json | JSON array of staged exercises | Upserted (Append or Update Row) on every GENERATE or MODIFY execution |

This table stores the current suggested workout between chat turns. It is keyed by session_id so multiple concurrent sessions are supported without interference. The row is upserted every time a new suggestion or modification is presented to the user, ensuring the staged_workout always reflects the latest state.

### 2.3 Key Design Principles

**Exercise Selection — 80/20 Rule**
- Body part focus is extracted from the prompt. Defaults to full body if not stated.
- Pool is filtered to matching body part. If no matches, falls back to full catalog.
- Pool is sorted by exercise_frequency ascending (least used first).
- Low-frequency pool: bottom 30% of sorted pool. High-frequency pool: top 70%.
- 80% of workout_size exercises picked randomly from high-frequency pool.
- 20% of workout_size exercises picked randomly from low-frequency pool.
- Selected exercises are then sorted by movement pattern rotation: squat, hinge, push, pull, rotation, carry.

**Volume Logic**
- Default mode is `same` — uses last logged reps/rounds/rep type for each exercise.
- Progressive mode applies +10% to repetition_amount, rounded up.
- For time-based exercises (repetition_type = time), the numeric value is parsed from strings like `30 sec` or `1 min`, incremented by 10%, and the unit is re-appended.
- If an exercise has never been logged, defaults to 10 reps and 3 rounds.
- User must explicitly request progressive — the default is same.

**State Management**
- No data is written to workout_exercise until the user types Confirm.
- Every GENERATE or MODIFY execution upserts the staged exercises to the staged_workout Google Sheets tab, keyed by session_id.
- CONFIRM flow reads from staged_workout and routes through the existing LOG pipeline.
- Interaction loop: Generate → Review → Modify (repeat) → Confirm → Log.

**Chat Output Format**
- Header line: Workout Focus | Patterns | Volume mode
- Second header line: Equipment needed
- Markdown table body: `# | Exercise | Rep Type | Amount | Rounds`
- New exercises (exercise_frequency = 0) are marked with a flag emoji
- Footer: reply options — Confirm, Replace, Add, Remove, Regenerate

### 2.4 Supported Modify Actions

| Action | User Trigger | Behaviour |
|---|---|---|
| replace | Replace [X] with [Y] | Removes exercise X from staged list (by name or index), adds Y from catalog with history lookup for reps/rounds |
| add | Add [X] | Appends exercise X to staged list. If not found in catalog, sets needs_new_exercise flag (currently unhandled — exercise is skipped) |
| remove | Remove [X] or Remove #N | Removes exercise from staged list by name or by 1-based index |
| regenerate | Regenerate / New suggestion | Re-runs full GENERATE flow. New parameters (body part, volume) can be specified in the same message |

**Exercise Name Fuzzy Matching**

Both catalog lookup (`findInCatalog`) and history lookup (`findInHistory`) use the same fuzzy matching logic to handle plural/singular variations between what the user types and what is stored:
- Exact match on exercise_name (case-insensitive)
- Match on exercise_name_normalized (lowercase singular form)
- Auto-plural: if name does not end in `s`, also try name + `s`
- Auto-singular: if name ends in `s`, also try name without the trailing `s`

### 2.5 n8n Workflow — GENERATE / MODIFY / CONFIRM Flows

**Flow Summary**
- **GENERATE:** route_by_intent TRUE → if_generate_or_modify TRUE → get_exercise_catalog → get_recent_workouts → code_workout_generator → code_format_suggestion → save_staged_workout → Respond to Webhook
- **MODIFY:** route_by_intent TRUE → if_generate_or_modify FALSE → get_exercise_catalog_modify → get_recent_workouts_modify → get_staged_workout → code_handle_modify → code_format_suggestion → save_staged_workout → Respond to Webhook
- **CONFIRM:** route_by_intent FALSE → if_log_or_confirm FALSE → get_staged_workout_confirm → code_confirm_to_log → code_json_output → (existing LOG pipeline from split_out_exercise onward)

**Node Reference — GENERATE / MODIFY / CONFIRM Flows**

| Node Name | Type | Purpose |
|---|---|---|
| route_by_intent | IF | generate or modify → TRUE branch. log or confirm_log → FALSE branch. |
| if_generate_or_modify | IF | generate → TRUE (GENERATE branch). modify → FALSE (MODIFY branch). |
| get_exercise_catalog | Google Sheets Get | Fetches full exercise_list for GENERATE flow including frequency data |
| get_recent_workouts | Google Sheets Get | Fetches full workout_exercise history for reps/rounds lookup |
| code_workout_generator | Code (JS) | Applies 80/20 selection, body part filter, movement pattern sort, progressive overload logic |
| code_format_suggestion | Code (JS) | Formats exercise list as Markdown table. Reads from $input.first() to handle both GENERATE and MODIFY sources. |
| save_staged_workout | Google Sheets Upsert | Upserts exercises_json to staged_workout tab keyed by session_id |
| get_exercise_catalog_modify | Google Sheets Get | Dedicated catalog fetch for MODIFY flow (separate from GENERATE to avoid shared state) |
| get_recent_workouts_modify | Google Sheets Get | Dedicated history fetch for MODIFY flow |
| get_staged_workout | Google Sheets Get | Reads current staged workout by session_id for MODIFY flow |
| code_handle_modify | Code (JS) | Applies replace/add/remove/regenerate to staged exercise list. Strips any prefix from exercises_json before parsing. |
| if_log_or_confirm | IF | log intent → TRUE (code_json_output). confirm_log → FALSE (confirm path). |
| get_staged_workout_confirm | Google Sheets Get | Reads staged workout by session_id for CONFIRM flow |
| code_confirm_to_log | Code (JS) | Converts staged exercises into LOG format compatible with code_json_output |

### 2.6 AI Agent System Prompt — All Intent Schemas

| Intent | Trigger Examples | Output Schema |
|---|---|---|
| log | Today I did..., I trained..., log my workout | `{ "intent": "log", "workout_date": "...", "workout_type_name": "...", "exercises": [...] }` |
| generate | Suggest a workout, Give me a workout, Generate lower body | `{ "intent": "generate", "body_part_focus": "...", "volume_logic": "same\|progressive", "workout_size": 5 }` |
| modify | Replace X with Y, Add X, Remove #N, Regenerate | `{ "intent": "modify", "action": "replace\|add\|remove\|regenerate", "exercise_name": "...", "new_exercise_name": "...", "exercise_index": N }` |
| confirm_log | Confirm, Log it, Save this, Yes, Looks good | `{ "intent": "confirm_log" }` |

### 2.7 code_workout_generator — Logic Detail

- Reads body_part_focus, volume_logic, workout_size from ai_agent_prompt_process output
- Filters exercise catalog by body part match (full body passes all exercises)
- Sorts filtered pool by exercise_frequency ascending
- Calculates `lowCount = max(1, round(workoutSize * 0.2))` and `highCount = workoutSize - lowCount`
- lowFreqPool = bottom 30% of sorted pool. highFreqPool = top 70% of sorted pool.
- Picks highCount exercises randomly from highFreqPool and lowCount from lowFreqPool
- Sorts selected exercises by movement pattern: squat → hinge → push → pull → rotation → carry
- For each exercise: calls getLastEntry to find most recent workout_exercise row by exercise name
- Applies volume logic: same = use last amounts as-is. progressive = `Math.ceil(reps * 1.1)` for reps, or parse and increment time string
- Returns array of enriched exercise objects with all fields needed for formatting

### 2.8 code_handle_modify — Logic Detail

- Reads staged workout from get_staged_workout node output
- Strips any text prefix before the JSON array character `[` as a safety fallback
- For replace: finds target exercise by name (fuzzy) or 1-based index. Looks up replacement in catalog. Looks up history entry for reps/rounds. Rebuilds list with replacement at same position.
- For add: looks up exercise in catalog using fuzzy name match. Looks up history. Appends to end of list. If not found in catalog, sets needs_new_exercise flag.
- For remove: finds target by name (fuzzy) or 1-based index. Rebuilds list without that exercise.
- For regenerate: outputs generate intent JSON to re-trigger GENERATE flow with new parameters.
- All results pass through code_format_suggestion for consistent formatting and staged_workout upsert.

## Part 3 — Open Tasks & Future Work

### 3.1 Known Issues & Improvements

| Item | Type | Description |
|---|---|---|
| Add new exercise to generator | Feature gap | When user adds an exercise not in catalog during GENERATE session, needs_new_exercise flag is set but no creation flow exists. Exercise is silently skipped. Needs routing through ai_agent_exercise_info pipeline. |
| workout_type_name in confirm | Bug | code_confirm_to_log hardcodes workout_type_name as full body. Should read body_part_focus from staged_workout row instead. |
| staged_workout cleanup | Maintenance | staged_workout sheet accumulates one row per session and is never purged. Add a scheduled cleanup workflow or TTL-based deletion. |
| Multiple sessions in one prompt | Limitation | Logging two separate workout sessions in one chat message is not supported. Each message generates one workout_id. |
| Regenerate preserves body part | Improvement | When user says Regenerate without specifying body part, agent should carry forward the body_part_focus from the previous suggestion rather than defaulting to full body. |

### 3.2 Phase 2 — Migration to Notion

**What Changes**
- All Google Sheets nodes replaced with Notion nodes
- Integer row IDs replaced with Notion Page IDs
- staged_workout Google Sheet replaced with Notion database
- ARRAYFORMULA calculated columns replaced with Notion relation and rollup properties

**What Stays the Same**
- All AI agent system prompts and JSON output contracts
- All Code node logic — code_workout_generator, code_handle_modify, code_workout_exercise, etc.
- All IF routing logic and node names
- Overall workflow structure and data flow

**Migration Steps**
1. Export all Google Sheets tabs to CSV
2. Create Notion databases: exercise_list, workout_type, workout_exercise, staged_workout
3. Import CSVs and add Notion relation properties between databases
4. Swap Google Sheets nodes for Notion nodes one flow at a time (LOG first, then GENERATE)
5. Update Code nodes where field names differ between Sheets and Notion
6. Regression test all 6 scenarios: log, suggest, replace, add, remove, confirm
