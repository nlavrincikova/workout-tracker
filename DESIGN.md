## Part 1 — Workout Tracker

### 1.1 Goal & Scope

A chat-driven AI Agent that logs workouts into a structured database, keeps a clean catalog of exercises, classifies workouts by type, and supports future analytics and recommendations.

Phase 1 uses Google Sheets as the backend for ease of debugging. Phase 2 will migrate to Notion with minimal workflow changes.

### 1.2 Data Model

**A. `exercise_list` — Master catalog (dimension table)**

| Column | Description | Notes |
|---|---|---|
| exercise_id | Unique integer ID | Primary key, auto-incremented by n8n |
| exercise_name | Canonical exercise name | Must be unique (case-insensitive) |
| exercise_body_part_focus | Main body area targeted | core / full body / lower body / upper body |
| exercise_primary_equipment | Equipment required | Nullable |
| exercise_movement_pattern | Movement classification | Squat / Hinge / Pull / Push / Carry / Rotate. Shown in workout suggestions. |
| exercise_intensity_type | Intensity category | Reps / Time / Load / AMRAP. Stored in the catalog but no longer displayed (replaced by movement pattern in the chat output). |
| exercise_description | One-sentence description | AI-generated by ai_agent_exercise_info |
| exercise_muscles_worked | Muscles targeted | AI-generated |
| exercise_key_cues_safety | Safety and form cues | AI-generated, optional |
| exercise_non_machine_alternative | Bodyweight alternative | AI-generated, optional |
| exercise_name_normalized | Lowercase singular name | Used for fuzzy matching in generator |
| exercise_frequency | Total times logged | Incremented by n8n after each confirmed workout |

**B. `workout_type` — Classification reference table**

| Column | Description | Notes |
|---|---|---|
| workout_type_id | Unique integer ID | Primary key |
| workout_type_name | Workout classification | e.g. full body, lower body, core. Unique, case-insensitive |

**C. `workout_exercise` — Fact table (transaction log)**

| Column | Description | Notes |
|---|---|---|
| workout_id | Session ID | Groups all exercises from one session |
| workout_date | Date of workout | Format: YYYY-MM-DD |
| workout_type_id | FK to workout_type | Required |

| workout_rounds | Number of rounds performed | Required |
| workout_repetition_type | Type of repetition | reps / time / amrap |

| workout_exercise_name | Calculated column | ARRAYFORMULA VLOOKUP from exercise_list tab |

### 1.3 Key Design Principles

**Separation of Responsibilities**
- **AI Agent decides:** exercise parsing and normalization, metadata generation for new exercises, workout type inference.
- **n8n enforces:** deduplication rules, ID generation, referential integrity, write order (dimension tables before fact tables).

**ID Strategy**
- All IDs are integers, auto-incremented by n8n using `max(existing) + 1`.
- New exercises are temporarily written with `PENDING` as the exercise_id placeholder.
- A subsequent Google Sheets Update node replaces `PENDING` with the calculated real ID.
- IDs are never generated by the AI agent.

**Deduplication Rules**

| Entity | Rule |
|---|---|
| Exercise | Case-insensitive exercise_name match. Falls back to exercise_name_normalized for plural/singular variants |
| Workout type | Case-insensitive workout_type_name match |
| Workout session | New workout_id generated per prompt execution — no deduplication |

### 1.4 n8n Workflow — LOG Flow

**Flow Summary**
1. Chat trigger → `ai_agent_prompt_process` parses workout into JSON
2. `route_by_intent` routes log intent to FALSE branch → `if_log_or_confirm` routes to `code_json_output`
3. `code_json_output` expands exercises array into individual items
4. `split_out_exercise` + `edit_exercise_name` normalizes each exercise name
5. `get_exercise_list` + `code_exercise_match` checks each exercise against catalog
6. New exercises: `ai_agent_exercise_info` generates metadata → `append_new_exercise` writes PENDING row → `code_exercise_id` calculates real ID → `update_exercise_id` replaces PENDING
7. All exercises merge → `get_workout_exercise` + `get_workout_types` → `code_workout_exercise` builds fact table rows
8. `append_workout_exercise` writes to workout_exercise → frequency counter increments → success message sent

**Response path.** The chat trigger runs in "When Last Node Finishes" mode, so whatever node executes last supplies the chat reply. Every path is built to end on `prepare_final_response`, and the chat page reads `response_text` from it. `Respond to Webhook` is present but disabled (it passes data through). Two consequences: a dead-end branch (for example a sheet update) must never be able to execute last, and switching the trigger to "Using Response Nodes" is not viable with the custom page — see §4.1.

### 1.6 Google Sheets ARRAYFORMULA Columns

The `workout_exercise` tab has two calculated columns. Formulas live in row 2 (not the header row, due to Google Sheets Table constraints) and auto-populate for all rows appended by n8n.

- **workout_type_name:** `=ARRAYFORMULA(IF(ISBLANK(C2:C), "", IFERROR(VLOOKUP(C2:C, workout_type!$A$2:$B$30, 2, FALSE), "Not Found")))`
- **workout_exercise_name:** `=ARRAYFORMULA(IF(ISBLANK(D2:D), "", IFERROR(VLOOKUP(D2:D, exercise_list!$A$2:$B$1000, 2, FALSE), "Not Found")))`

## Part 2 — Workout Generator

### 2.1 Goal & Scope

A read-analyze-suggest pipeline that generates tailored workout suggestions based on historical performance and catalog availability. No data is written to workout_exercise until the user explicitly confirms the suggestion.

### 2.2 Additional Data Model

**D. `staged_workout` — Session staging table**

| Column | Description | Notes |
|---|---|---|
| session_id | Chat session identifier | From When chat message received node sessionId field. Also stored in browser localStorage for session persistence. |
| exercises_json | JSON array of staged exercises | Upserted on every GENERATE or MODIFY execution |
| body_part_focus | Body part of the current suggestion | Used by the CONFIRM flow to set workout_type_name |
| suggestions_json | JSON array of replacement candidates | Populated by suggest_replacements. Holds the candidate exercises the user picks from. |
| target_index | Index of the exercise being replaced | 0-based index into exercises_json. Used by replace_selection to know which exercise to swap out. |
| original_request_json | Verbatim JSON of the original GENERATE request (body_part_focus, volume_logic, workout_size) | Written by code_workout_generator on every GENERATE and carried forward unchanged by replace/add/remove/regenerate. Plain "regenerate" replays this instead of trusting the agent's regenerate-schema defaults. |

This table stores the current suggested workout between chat turns. It is keyed by session_id so multiple concurrent sessions are supported without interference, and it is upserted every time a suggestion or modification is presented, so it always reflects the latest state.

**Design note — `original_request_json`.** Storing the agent's original request verbatim (rather than a hand-picked subset of fields) means any field added to the GENERATE request in future is replayed by `regenerate` automatically, with no regenerate-specific code changes. The same pattern is reusable wherever a flow needs to "remember" the original request across modify actions.

### 2.3 Key Design Principles

**Exercise Selection — 80/20 Rule**
- Body part focus is extracted from the prompt. Defaults to full body if not stated.
- Pool is filtered to matching body part. If no matches, falls back to full catalog.
- Pool is sorted by exercise_frequency ascending (least used first).
- Low-frequency pool: bottom 30% of sorted pool. High-frequency pool: top 70%.
- 80% of workout_size exercises picked randomly from the high-frequency pool, 20% from the low-frequency pool.
- Selected exercises are sorted by movement pattern rotation: squat, hinge, push, pull, rotation, carry.

**Volume Logic**
- Default mode is `same` — uses last logged reps/rounds/rep type for each exercise.
- Progressive mode applies +10% to repetition_amount, rounded up. The user must explicitly request it.
- For time-based exercises, the numeric value is parsed from strings like `30 sec` or `1 min`, incremented by 10%, and the unit is re-appended.
- If an exercise has never been logged, defaults to 10 reps and 3 rounds.

**State Management**
- No data is written to workout_exercise until the user types Confirm.
- Every GENERATE or MODIFY execution upserts the staged exercises to the staged_workout tab, keyed by session_id.
- CONFIRM reads from staged_workout and routes through the existing LOG pipeline.
- Interaction loop: Generate → Review → Modify (repeat) → Confirm → Log.

**Chat Output Format**
- `code_format_suggestion` emits structured plain text; the chat page (Part 3) parses it into a card.
- Header: Focus | Volume mode | Patterns | Equipment needed
- Numbered exercise list, each with `rounds x amount rep_type`, then Body Part Focus, Muscles Worked and Movement Pattern detail lines.
- A `NEW` tag marks exercises with exercise_frequency = 0.
- Optional `Note:` line under the header when a modify action failed (e.g. the exercise to replace was not found) — see §2.8.
- Footer: reply options — Confirm, Replace, Suggest replacements, Add, Remove, Regenerate.
- Movement Pattern replaced Intensity Type in the display because it is more actionable for workout planning.

### 2.4 Supported Modify Actions

| Action | User Trigger | Behaviour |
|---|---|---|
| replace | Replace [X] with [Y] | Removes exercise X (by name or index), adds Y from the catalog with a history lookup for reps/rounds. |
| suggest_replacements | Suggest replacements for [X] | Shows 3 candidate exercises for the user to pick from, preferring the same movement pattern, then the same body part. Excludes exercises already in the workout. Candidates are stored in `staged_workout.suggestions_json`. |
| replace_selection | 1, 2 or 3 (after seeing suggestions) | Applies the chosen candidate at the stored `target_index` and shows the updated workout. |
| add | Add [X] | Appends exercise X. If X is not in the catalog, the catalog-extension path below creates it first. |
| remove | Remove [X] or Remove #N | Removes exercise by name or 1-based index. An unmatched name or out-of-range index sets an error, shown as a Note banner instead of silently no-op'ing. |
| regenerate | Regenerate / New suggestion | Replays the original GENERATE request from `original_request_json` (same focus, volume mode and size) with a fresh random selection. Inline overrides ("regenerate but upper body") are not supported yet. |

**Catalog Extension (`needs_new_exercise`)**

When `add` targets an exercise that fuzzy matching cannot find in the catalog, `code_handle_modify` sets a `needs_new_exercise` flag instead of skipping it. The flow then:
1. `check_needs_new_exercise` routes flagged results into the extension branch (everything else goes straight to formatting).
2. `prep_new_exercise_name` → `ai_agent_exercise_info_modify` generates the same metadata fields as the LOG-flow extension path.
3. `code_json_output3` → `append_new_exercise_modify` writes the row with a `PENDING` ID (same ID strategy as §1.3) → `get_pending_exercise_id_modify` → `code_exercise_id_modify` calculates the real ID.
4. `update_exercise_id_modify` replaces `PENDING` in the sheet, then `code_resume_add` appends the new exercise (default 3 rounds x 10 reps, tagged NEW) to the staged workout and hands it to `code_format_suggestion`. The two steps are strictly sequential: they used to run as a parallel fork, and because the reply is the last node's output, the dead-end sheet update could run last and leak its raw output into the chat.

**Exercise Name Fuzzy Matching**

Both catalog lookup (`findInCatalog`) and history lookup (`findInHistory`) use the same logic to handle plural/singular variations between what the user types and what is stored:
- Exact match on exercise_name (case-insensitive)
- Match on exercise_name_normalized (lowercase singular form)
- Auto-plural: if the name does not end in `s`, also try name + `s`
- Auto-singular: if the name ends in `s`, also try the name without the trailing `s`

### 2.5 n8n Workflow — GENERATE / MODIFY / CONFIRM Flows

**Flow Summary**
- **GENERATE:** route_by_intent TRUE → if_generate_or_modify TRUE → get_exercise_catalog → get_recent_workouts → code_workout_generator → code_format_suggestion → save_staged_workout → prepare_response → prepare_final_response (reply)
- **MODIFY:** route_by_intent TRUE → if_generate_or_modify FALSE → get_exercise_catalog_modify → get_recent_workouts_modify → get_staged_workout → code_handle_modify → check_needs_new_exercise → (catalog-extension branch when flagged) → code_format_suggestion → save_staged_workout → prepare_response → prepare_final_response (reply)
- **CONFIRM:** route_by_intent FALSE → if_log_or_confirm FALSE → get_staged_workout_confirm → code_confirm_to_log → code_json_output → (existing LOG pipeline from split_out_exercise onward)

### 2.7 code_workout_generator — Logic Detail

- Reads body_part_focus, volume_logic, workout_size from ai_agent_prompt_process output
- Filters exercise catalog by body part match (full body passes all exercises)
- Sorts filtered pool by exercise_frequency ascending
- Calculates `lowCount = max(1, round(workoutSize * 0.2))` and `highCount = workoutSize - lowCount`
- lowFreqPool = bottom 30% of sorted pool. highFreqPool = top 70% of sorted pool.
- Picks highCount exercises randomly from highFreqPool and lowCount from lowFreqPool
- Sorts selected exercises by movement pattern: squat → hinge → push → pull → rotation → carry
- For each exercise: finds the most recent workout_exercise row by exercise name
- Applies volume logic: same = use last amounts as-is. progressive = `Math.ceil(reps * 1.1)` for reps, or parse and increment the time string
- Stores the raw agent output as `original_request_json`
- Returns an array of enriched exercise objects with all fields needed for formatting

### 2.8 code_handle_modify — Logic Detail

- Reads the staged workout from get_staged_workout; a parse failure degrades to an empty list rather than an error.
- **replace:** finds the target by name (fuzzy) or 1-based index, looks up the replacement in the catalog and its history entry, and rebuilds the list with the replacement in the same position.
- **suggest_replacements:** finds the target, then builds a candidate pool excluding exercises already in the workout — same movement pattern first, falling back to same body part, then to the whole catalog. The pool is sorted by frequency and 3 candidates are picked at random from the least-used slice. Sets `suggestion_mode` so the formatter renders a pick-one list instead of the full workout.
- **replace_selection:** reads `suggestions_json` and `target_index` from staged_workout and swaps the chosen candidate into place.
- **add:** fuzzy catalog lookup and history lookup, appended to the end. If not found, sets `needs_new_exercise` (see §2.4).
- **remove:** finds the target by name (fuzzy) or 1-based index and rebuilds the list without it.
- **regenerate:** replays `original_request_json` and re-runs the same 80/20 selection inline (it mirrors code_workout_generator, because the canvas has no path back to that node).
- **Error handling:** failed replace (target or replacement not found), failed suggest_replacements, and invalid or missing replace_selection all set `error_message` on the result. `code_format_suggestion` renders it as a `Note:` line above the unchanged workout, and the chat page shows it as a warning banner.
- Every result carries `original_request_json` forward from the staged row and clears stale `suggestions_json` / `target_index` unless the action set them.

## Part 3 — Custom Chat Interface

### 3.1 Goal & Scope

A mobile-friendly dark-themed HTML chat page that renders workout suggestions as formatted cards. It is hosted by n8n itself, as a dedicated webhook workflow, and supports session persistence so a workout generated in the morning can be confirmed in the evening.

### 3.2 Architecture

| Component | Detail |
|---|---|
| URL | `https://YOUR-N8N-HOST/webhook/workout-tracker` |
| Hosting | n8n webhook workflow (`workout_tracker_page`) serving HTML from a Code node |
| Workflow | 3 nodes: Webhook (GET) → Code in JavaScript → Respond to Webhook (text/html) |
| Reason for Code node | HTML served via the Respond to Webhook body field corrupted the embedded JavaScript. A Code node handles large content reliably. |
| Chat endpoint called by page | `https://YOUR-N8N-HOST/webhook/YOUR-CHAT-WEBHOOK-ID/chat` (the main workflow) |
| Staged workout API | `https://YOUR-N8N-HOST/webhook/get-staged-workout` (`workout_tracker_get_staged_workout_api` workflow: Webhook → Google Sheets lookup by session_id → Respond to Webhook) |
| Session ID | Generated client-side, persisted in localStorage, reused on page reload |
| Tech stack | Vanilla HTML/CSS/JS — no framework, no dependencies except Google Fonts |
| CDN note | The domain sits behind Cloudflare, which adds a sandbox Content-Security-Policy header. A Transform Rule removes that header for the page path so inline scripts and localStorage work. |

### 3.3 Session Persistence

Users often generate a workout in the morning and want to confirm it later. Without persistence, a page refresh loses the session ID and the staged workout cannot be retrieved.

- On first page load a new session_id is generated and saved to localStorage; later loads reuse it.
- On load, the page calls the staged workout API with the stored session_id.
- If a staged workout exists, a banner appears: "You have an unsaved workout from earlier".
- **View** rebuilds the workout card from the staged_workout data. **Dismiss** generates a new session_id and abandons the old staged workout.
- Generating a new workout overwrites the staged_workout row for that session_id.
- The page test-writes to localStorage on load; if storage is blocked it silently degrades to a non-persistent session.

### 3.4 Features

- Dark theme matching the n8n colour palette
- Welcome screen with quick-reply chips for common requests
- Typing indicator while waiting for a response
- Unsaved-workout banner on page load when a staged workout is detected
- Workout suggestion rendered as a structured card with header meta tags
- Warning banner at the top of the card when the backend reports a failed modify action
- Per-exercise rows: name, NEW badge, rounds x amount rep_type, Body Part Focus, Muscles Worked, Movement Pattern
- Replacement suggestion card with 3 options and clickable 1/2/3 buttons
- Clickable quick-reply buttons in the card footer
- Plain-text responses rendered in a monospace bubble
- Auto-resizing textarea, Enter to send, Shift+Enter for newline
- Mobile-friendly responsive layout using `100dvh`

### 3.5 Response Parsing

The backend returns plain text; the page reconstructs the card client-side by matching line prefixes. Anything the parser does not recognise is dropped, which is why a new kind of line (like `Note:`) needs a matching parser and renderer change.

- A response containing the `WORKOUT SUGGESTION` header (or a `Focus:` line) builds the standard workout card
- A response containing replacement options builds the replacement card
- Everything else falls back to a plain-text bubble
- Header lines: `Focus:`, `Volume:`, `Patterns:`, `Equipment:`, and the optional `Note:` (rendered as the warning banner)
- Numbered exercises (`1. Exercise Name`), the volume line (`N rounds x Amount rep_type`), and the Body Part Focus / Muscles Worked / Movement Pattern detail lines
- Footer reply options (lines starting with `>`)
- Backslash escape sequences are doubled inside the template literal so they survive JavaScript execution

### 4.2 Phase 2 — Migration to Notion

**What Changes**
- All Google Sheets nodes replaced with Notion nodes
- Integer row IDs replaced with Notion Page IDs
- staged_workout Google Sheet replaced with a Notion database
- ARRAYFORMULA calculated columns replaced with Notion relation and rollup properties

**What Stays the Same**
- All AI agent system prompts and JSON output contracts
- All Code node logic — code_workout_generator, code_handle_modify, code_workout_exercise, etc.
- All IF routing logic and node names
- The custom HTML chat interface and session persistence logic

**Migration Steps**
1. Export all Google Sheets tabs to CSV
2. Create Notion databases: exercise_list, workout_type, workout_exercise, staged_workout
3. Import CSVs and add Notion relation properties between databases
4. Swap Google Sheets nodes for Notion nodes one flow at a time (LOG first, then GENERATE)
5. Update Code nodes where field names differ between Sheets and Notion
6. Regression test all scenarios: log, suggest, suggest replacements, replace, add, remove, regenerate, confirm
